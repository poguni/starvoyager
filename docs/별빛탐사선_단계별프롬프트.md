# 별빛 탐사선 (Star Voyager) 단계별 개발 프롬프트

> 기준 문서: `별빛탐사선_기획서.md`
> 참고 프로젝트: 달빛 관측소(MoonLab) 저장소와 `Development_Report_v1.md`
> 디자인 자료: `design/` 폴더 (만드는 방법은 `별빛탐사선_디자인브리프.md`)
> 대상 도구: Claude Code
> 개정: 디자인 시안(`design/`)을 먼저 준비하고, Phase 1부터 화면 요소를 시안 기준으로 만드는 방식으로 Phase 1~9B 수정. Phase 8은 '시안 대조 다듬기'로 변경.

---

## 0. 이 문서 사용법

### 0-1. 진행 원칙
- Phase는 **1 → 10 순서**로 진행한다. 각 Phase의 **완료 확인**을 모두 통과한 뒤에만 다음 Phase로 넘어간다.
- 각 Phase의 프롬프트(회색 상자)를 Claude Code에 **그대로 붙여 넣는다.** `[ ]`로 표시된 곳은 붙여 넣기 전에 채운다.
- Phase를 시작할 때마다 Claude Code가 **계획을 먼저 보여 주고**, 승인한 뒤에 구현하도록 프롬프트에 적어 두었다.
- Phase가 끝나면 커밋하고, 다음 Phase는 새 대화(`/clear`)로 시작해도 된다. 프로젝트 규칙은 `CLAUDE.md`(0-3)에 있어 대화가 바뀌어도 유지된다.
- 개발 중 기획서와 다르게 정한 내용은 `docs/결정기록.md`에 쌓는다(달빛 관측소 리포트 6-3절과 같은 역할).

### 0-2. 시작 전 준비 (사용자가 할 일)
1. 새 폴더 `StarVoyager/`를 만들고 그 안에 `별빛탐사선_기획서.md`, 이 문서, `별빛탐사선_디자인브리프.md`를 넣는다.
2. **디자인 자료를 먼저 준비한다.** `별빛탐사선_디자인브리프.md`의 순서대로 클로드 디자인에서 시안을 만들고, 6장에 따라 `StarVoyager/design/` 폴더를 채운다. 전달 방법은 0-4절.
   - 디자인 패키지(`StarVoyager_design.zip`)를 받았다면 압축을 풀어 `StarVoyager/design/`에 두면 이 준비가 끝난다(A 관제실형으로 확정, 화면 S01~S10 포함).
   - 직접 만드는 경우 최소한 `design/tokens.css`, `design/design-system.png`, `design/motion.md`, `design/README.md`, `design/screens/S03`·`S04`는 Phase 1 전에 있어야 한다. 나머지 화면은 그 화면을 쓰는 Phase 전까지만 준비되면 된다(`design/README.md` 표의 'Phase' 열 참고).
3. 달빛 관측소 저장소가 같은 상위 폴더에 있는지 확인한다. (예: `작업폴더/MoonLab/`, `작업폴더/StarVoyager/`)
   - 위치가 다르면 아래 프롬프트의 `../MoonLab` 경로를 실제 경로로 바꾼다.
4. 기획 단계에서 정한 두 가지 결정(기획서 17장)은 이미 각 Phase 프롬프트에 반영되어 있다.
   - 수성 회색, 목성 흰색과 갈색 줄무늬 → Phase 5
   - 북쪽 밤하늘 날짜 고정 → Phase 7 (정확한 날짜는 Phase 7에서 계산한 후보 중 고른다)
5. GitHub 저장소 `poguni/starvoyager`는 Phase 10에서 만들어도 된다.

### 0-3. `CLAUDE.md` (Phase 1에서 Claude Code가 만든다)
Phase 1 프롬프트가 아래 내용으로 `CLAUDE.md`를 만들게 되어 있다. 이후 규칙을 바꾸고 싶으면 이 파일을 직접 고치면 된다.

```
# 별빛 탐사선 (Star Voyager) 프로젝트 규칙

## 기준 문서
- 요구사항: 별빛탐사선_기획서.md (모든 판단의 기준)
- 개발 순서: 별빛탐사선_단계별프롬프트.md
- 참고 코드: ../MoonLab (달빛 관측소, 같은 구조·같은 규칙으로 만든 앱)
- 결정 기록: docs/결정기록.md

## 작업 방식
- 구현 전에 계획을 먼저 보여 주고 승인을 받는다.
- 기획서에 없거나 기획서와 다르게 하고 싶은 것은 임의로 정하지 말고 먼저 묻는다. 정해진 내용은 docs/결정기록.md에 날짜와 함께 적는다.
- 지금 Phase의 범위만 만든다. 다음 Phase 기능을 미리 만들지 않는다.
- Phase가 끝나면 '완료 확인' 항목을 직접 점검한 결과를 보고한다.

## 코드 규칙
- Vite + 순수 JavaScript(ESM). TypeScript·React 등 프레임워크를 쓰지 않는다.
- 계산·판정 로직은 src/model, src/missions 등 DOM과 분리된 순수 모듈로 만들고 Vitest로 테스트한다.
- Three.js 장면은 src/scene, DOM 조작은 src/ui에 둔다.
- 앱 본체는 외부 CDN을 쓰지 않는다(질감·글꼴·별 데이터 모두 저장소에 포함).
- npm test가 항상 통과해야 한다.

## 화면 문구 규칙
- 학생에게 보이는 문구는 초등 4학년 수준의 짧은 해요체로 쓴다.
- 교과서 용어만 쓴다: 충돌 구덩이(크레이터 X), 표면이 기체로 된 행성(가스 행성 X), 행성·위성·혜성·소행성·별·별자리.
- 기획서에 적힌 학생용 문구는 한 글자도 바꾸지 않는다.
- 지구 표면에 지명을 표시하면 동해로 표기한다.

## 디자인
- 디자인 자료는 design/ 폴더에 있다. 목차는 design/README.md.
- 내용(문구, 보기, 정답, 기능)은 기획서가 기준이고, 겉모습(색, 글꼴, 크기, 간격, 모양, 움직임)은 design/이 기준이다.
- 색·글꼴·크기·간격 값은 src/styles/tokens.css(design/tokens.css에서 옮긴 것)의 CSS 변수만 쓴다. 코드에 색상값을 직접 쓰지 않는다.
- 화면을 만들거나 고치기 전에 해당 시안(design/screens/S01~S10)을 열어 보고, 만든 뒤에는 같은 크기(1920×1080, 크롬북은 1366×768)로 스크린샷을 찍어 시안과 나란히 비교한다.
- 움직임은 design/motion.md의 길이와 방식을 따른다.
- 시안에 없는 화면·상태는 디자인 시스템으로 만들되 먼저 묻는다. 시안과 다르게 만든 것은 design/README.md의 '디자인과 다르게 정한 것' 표에 적는다.
- 시안 속 배경 행성 사진은 자리 표시용이다. 앱에 넣지 않는다.

## 개인정보
- 학생 이름은 구글 시트로 보내는 요청 본문 외에 콘솔 로그·오류 메시지·화면 디버그 패널 어디에도 남기지 않는다.

### 0-4. 디자인 자료를 Claude Code에 전달하는 방법

**원칙: 대화창에 붙여 넣지 말고 파일로 둔다.** 시안 이미지와 CSS를 대화에 직접 붙여 넣으면 대화가 바뀔 때(`/clear`) 사라지고, 다음 Phase에서 다시 설명해야 한다. `design/` 폴더에 두고 `CLAUDE.md`와 프롬프트에서 파일 이름으로 가리키면, 어느 Phase에서든 Claude Code가 필요한 시안을 직접 열어 본다(Claude Code는 PNG 이미지를 읽어 볼 수 있다).

**전달 경로 세 갈래**
| 무엇 | 어떻게 전달되나 |
|---|---|
| 디자인 값(색·글꼴·크기·간격·강조 색 11개) | `design/tokens.css` → Phase 1에서 `src/styles/tokens.css`로 옮겨 **앱 전체의 단 하나의 기준**이 된다 |
| 화면 모양 | `design/screens/S01~S10.png`(+ 있으면 `design/html/`) → 각 Phase 프롬프트가 해당 화면 번호를 가리킨다 |
| 움직임 | `design/motion.md` → 비행·착륙·도감·미션 연출을 만드는 Phase가 읽는다 |

**확인 습관**
- 화면을 만든 Phase가 끝나면 "시안과 나란히 비교한 스크린샷을 보여 달라"고 한다(부록의 짧은 프롬프트). 눈으로 보고 다른 점을 말로 짚어 주면 가장 빨리 맞춰진다.
- 차이를 짚을 때는 "S04의 도감 머리띠 높이가 시안보다 낮아요"처럼 **화면 번호 + 부품 이름**으로 말한다. 디자인 시스템의 부품 이름(디자인브리프 3장)을 그대로 쓰면 오해가 적다.

**디자인을 고치고 싶을 때**
- 작은 수정(색 하나, 간격 조금): `design/tokens.css`를 고치고 Claude Code에 "design/tokens.css가 바뀌었어요. src/styles/tokens.css에 반영해 주세요"라고 한다.
- 화면 수정: 클로드 디자인에서 시안을 고쳐 같은 파일 이름으로 덮어쓰고 "S05 시안이 바뀌었어요. 다시 보고 맞춰 주세요"라고 한다.
- 시안을 버리고 화면에서 직접 정한 것은 `design/README.md`의 '디자인과 다르게 정한 것' 표에 남긴다.

## Phase 1. 프로젝트 초기화 + 공통 모듈 이식 + 시트 두 탭 제출 테스트 + 디자인 기반

**목표**: 달빛 관측소의 검증된 뼈대를 가져와 새 프로젝트를 세우고, 구글 시트의 '미션'·'도감' 두 탭에 실제로 기록되는지 가장 먼저 확인한다. 디자인 시스템을 코드로 옮겨 이후 모든 화면의 기반을 만든다.

**사전 준비**: 새 구글 시트를 하나 만들어 둔다(달빛 관측소 시트와 분리 권장). `design/` 폴더가 0-2절 2번의 최소 조건을 채웠는지 확인한다.

```
